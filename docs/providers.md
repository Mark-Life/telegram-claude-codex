# Providers: Codex, Claude Code and pi

## What the bot looks for

**Codex CLI** (`codex`). There is no setting that turns a provider on: at startup the bot looks for each provider's CLI and asks it whether its account is logged in (`codex login status`), 5 s at most each. It logs one line per provider, `Codex CLI: <path>` with its `status` (`ready`, `logged_out`, `missing`, `unknown` when the check timed out). It keeps running when nothing is ready, but every run fails until an account is connected. It finds the binary itself — `PATH` first, then `~/.local/bin`, `~/bin`, `~/.bun/bin`, `~/.codex/bin` — and finds one installed after boot at the next check. Set `CODEX_BIN` if yours lives anywhere else. Do not rely on `which codex` in your terminal: a systemd unit inherits `PATH` from `/etc/environment`, not from the shell rc file that put `~/.local/bin` on yours. **Claude Code** (`claude`), optional, found and checked the same way. Install it as the service account (`curl -fsSL https://claude.ai/install.sh | bash`) and log in with `claude auth login`. A `claude` on `PATH` or in `~/.local/bin`, `~/bin`, `~/.bun/bin`, `~/.claude/local` only tells the bot Claude is installed: runs use the CLI that `@anthropic-ai/claude-agent-sdk` ships, pinned with it (`bun install` pulls about 236 MB for it), and the account check runs `auth status` on that binary. Set `CLAUDE_BIN` to run another one. The check confirms a login exists, not that it still works: a revoked token reads `ready` and every Claude run fails until you log in again or switch with `/provider`. With both Codex and Claude ready, new conversations start on Codex; `/provider` changes a conversation. Claude serves the address judge's fallback (no `TYPESAFE_API_KEY`, or its call failed) when Codex is not ready, or when it is picked for it in «Служебные проходы». Claude's group, guest and Business runs get no local tools at all, only web search: those senders are people you do not control. Members get file tools in the sandbox view, as on Codex; without both `bwrap` and `socat` they are refused. The view keeps Claude's real credentials file, so runs bill your subscription, and a member's shell could read that file: grant `member` only to people you would trust with it. Executor, the Telegram account and group memory work on Claude too: the bot holds the Executor and account tokens and passes each tool call on itself, so a Claude child never sees them.

## Connect the Codex account

From the chat, as the owner:

```
/login
```

It lists every account the bot signs in to, with its status: the owner's Telegram account and each provider with a device flow (Codex today). For Codex the status is what `codex login status` says; when the machine is not authenticated, «Войти: Codex» runs `codex login --device-auth`: the link and the code are posted into the chat, you approve them on any device, and the bot confirms once the process exits. It waits ten minutes, then kills the child — send `/login` again to retry. «Отменить вход: Codex» kills it sooner. Signing out of Codex stays in the shell (`codex logout`), since every run bills to that account.

The alternative is `codex login` in a shell **as the service account** (`sudo -iu bot codex login`). Logging in as the wrong user leaves the credentials where the service cannot read them.

If the account is missing at boot the startup message says so instead of failing. A successful Codex sign-in, or a `/login` that finds the account already connected from a shell, checks every provider again without a restart.

If `/login` shows `Codex: не установлен на сервере.`, the bot found no CLI at boot: `journalctl --user -u bot | grep 'CLI'` shows what it looked for. Install it or set `CODEX_BIN` to the real path, and restart. `Не удалось запустить подключение. Попробуйте позже.` means the CLI was found but would not start.

A conversation stays on the provider it started on. A forum topic keeps the provider in its row; when that provider cannot run, a message there is answered with one sentence instead of moving the topic elsewhere. A new topic starts on the default provider of whoever writes in it first (Новые беседы in `/settings`), when they chose one and it can run. The owner's private chat follows the owner's own choice when one is stored, else the detected default. Everything else, executors' private chats outside a topic included, takes the detected default: the first provider that is ready. A topic in an executor's private chat was pinned by a run or by their `/new`, never by `/provider`, so when its provider cannot run it moves to their own default provider (else the detected one) and starts a new conversation. The owner and executors share the private-chat conversation of one project and provider.

`/provider` (owner only, listed once two or more providers are installed) changes the provider of the conversation it is sent in: a forum topic of the workspace, for the owner and executors writing there, or the owner's private chat. A switch starts a new conversation and stops whatever was running there. In the private chat it also clears the stored conversation on the new provider, which executors share. Groups, guests, members and Business replies always run on the light provider, in a topic too.

## Connect the Claude account

`/login` has no entry for Claude yet. In a shell, as the service account: `claude auth login`. `/provider` and a refused message check again without a restart, so the login shows up there. Which provider new conversations default to is decided at boot and after a Codex `/login`, so restart (`systemctl --user restart bot`) when Claude should become the default. `journalctl --user -u bot | grep -i claude` shows `Claude CLI: <path>` with its status.

## pi

pi (`pi`, 1.6.x from its managed installer) is found like the others: `PI_BIN`, then `PATH`, then `~/.pi/agent/bin`, `~/.local/bin`, `~/bin`, `~/.bun/bin`. It is `ready` when it has a model (`PI_DEFAULT_MODEL`, else `defaultProvider/defaultModel` in `~/.pi/agent/settings.json`) and `pi auth check --no-refresh` finds credentials for it; with no model it reads `logged_out`. A default that may not run (a local one, below) leaves pi ready while it has another model to pick, with one warning in the log; with none left, pi reads `logged_out`. A version outside 1.4.x logs a warning and is still used. Setup, keys and a `models.json` example: [README](../README.md#set-up-pi).

Each run starts its own `pi --mode rpc` child with every discovery switched off: no extensions, MCP servers, skills of pi's own, prompt templates, themes or `AGENTS.md`/`CLAUDE.md` files, nothing project-local (`.pi/`), nothing installed or fetched at startup. Your own and executor runs are told your workspace `AGENTS.md` and pi's `~/.pi/agent/AGENTS.md` by the bot instead ([usage](usage.md#personal-rules-and-skills)), and load the bot's skills (sending a file, recurring tasks and, for you, access, profile, self-update and upstream sync), as on Codex and Claude. A message that starts with `/` is plain text, except `/skill:<name>` of one of those skills, which loads that skill with the rest of the message. Your own runs keep pi's sessions in `~/.pi/agent/sessions` and resume them; `/compact` uses pi's own compaction and keeps the session; `/context` shows pi's own estimate. A message sent while pi works joins the running task, as on Codex and Claude. `/usage` says, when pi is ready, that the bot does not show its limits.

**Picking a model on pi.** pi has no automatic model choice: a conversation runs on its default (`PI_DEFAULT_MODEL`, else pi's `settings.json`, or your own pi pick in Мои настройки → Новые беседы) until you pick another. `/model` shows up to eight model buttons, «По умолчанию» included: the current pick, «По умолчанию», your favourites, the last five models picked with `/model`, then the models of small providers from `models.json`. A pick that is no longer on the list keeps its marked row with «сейчас недоступна», so you can see what the conversation runs on and pick another. Favourites are pi's own `enabledModels` in `~/.pi/agent/settings.json` (the list `pi`'s Ctrl+P cycles through, edited with `/scoped-models` in pi), as exact `provider/id`s or globs such as `"openrouter/anthropic/claude-*"`; a `:high` suffix is ignored. Below them, «Все модели» sends every model id grouped by provider, each tappable to copy; a provider with more than 15 models (OpenRouter) gets one line with its count and a search to send. `/model <words>` searches: a full `provider/id`, or an id only one provider has, is set at once; otherwise every word must appear in the id or the model's name, and up to eight matches come back as buttons (`/model openrouter claude sonnet`). `/effort` offers the levels the model's thinking setting takes, and says so when it has none. The model list is read from pi when `/model` or a `/settings` picker opens, at most once an hour, and also by the bot's cleanup pass, which runs right after start and every 3 hours and reads the list once pi is `ready` and the one in hand is over a day old; so the list, and every `!command` key below, is read soon after a restart and about once a day even if nobody opens `/model`. While the first read is still running (a few seconds, longer with a slow `!command` key) `/model`, `/effort` and the `/settings` pickers say the list is loading. A button from an older list asks you to open `/model` again.

Only providers whose key works are offered. pi lists a provider whose `apiKey` is a `!command` without running it, so the bot runs each such command itself (3 s at most, its output never kept or logged) and leaves out every provider whose `auth.json` or `models.json` key, or one of its `models.json` `headers`, comes out empty: with no OpenRouter key, no OpenRouter model shows in `/model`, its search, «Все модели» or the `/settings` pickers. Groups, guests, members, Business replies and the helper passes below get no provider key from the bot's env, so a provider keyed only there (Groq through the bot's `GROQ_API_KEY`, with no `groq` entry in `auth.json` or `models.json`) is offered for your own runs (`/model`, Новые беседы) and left out of «Группы и гости» → Модель. With `bwrap` those runs also resolve a `!command` key or header inside the sandbox view, which holds only pi's files listed below, so the bot checks it there for them: `!sh -c '. ~/.pi/agent/.env.local; …'` works for them, while `!cat ~/.config/openrouter.key` or `!pass show openrouter` works only for your own runs and keeps the provider out of «Группы и гости» too. A light pick or `PI_LIGHT_MODEL` on such a model is skipped for the next one in line. When no model is left for them, «Группы и гости» → Модель and the screen's note on helper passes say so; put a key in `auth.json` or `models.json`.

Local models are switched off for now, for every run, yours included. A model whose `baseUrl` is, or resolves to, a non-public address (loopback such as `http://127.0.0.1:11434/v1` or `localhost`, the LAN, the tailnet, link-local) is left out of `/model`, its search, «Все модели», the favourites, the recent picks and the `/settings` pickers, and a light pick or `PI_LIGHT_MODEL` on one is skipped for the next in line. A conversation or a light choice that still names one fails with the usual error, and the log says `runs on a local endpoint`; so does a model pi does not list, whose endpoint cannot be checked. A conversation with no pick of its own runs on pi's default, so with a local default it fails too: `/model` shows the default row as «(сейчас недоступна)», pick a model below it. A remote server on a custom port (`https://gpu.example.com:8443/v1`) is not local. The check fails closed: a model runs only when pi sends it to an `http`, `https`, `ws` or `wss` URL whose host resolves to public addresses, so a model with no such URL is left out and refused too: Azure without `AZURE_OPENAI_RESOURCE_NAME`, and Google Vertex, whose catalog URL is a `{location}` template. A GitHub Copilot login is checked at the host pi really sends it to: the one its token names, or `copilot-api.<your enterprise host>`. A model whose host does not resolve (DNS down, at boot say) stays listed and pi stays ready, but a run on it is refused until the name resolves, since it cannot be checked; the log says `does not resolve`. pi children never get a variable that moves a model past the `baseUrl` pi lists (`AZURE_OPENAI_BASE_URL`, `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL`, `AWS_ENDPOINT_URL*` and the like; the full list is in the [README](../README.md#set-up-pi)), and a key in `auth.json` whose `env` sets one is refused, as is every model when `auth.json` is there but does not parse. The shell commands of your own full-access pi runs inherit that env: they lose `AZURE_OPENAI_BASE_URL`, `AZURE_OPENAI_ENDPOINT`, `OPENAI_BASE_URL`, `ANTHROPIC_BASE_URL`, `GOOGLE_GEMINI_BASE_URL`, `GOOGLE_VERTEX_BASE_URL`, `LLAMA_BASE_URL`, every `AWS_ENDPOINT_URL*` and a `GOOGLE_CLOUD_LOCATION` that is not a plain region name, and get `AWS_IGNORE_CONFIGURED_ENDPOINT_URLS=true`, so the `aws` CLI inside a pi run ignores `endpoint_url` in `~/.aws/config` (R2, MinIO) and goes to AWS. A script that needs one of them (an OpenRouter key behind `OPENAI_BASE_URL`, say) works on Claude and Codex, whose runs are unchanged, and not on pi: handing the names back to tools would let a script reach a local model.

Topic titles and the format pass of script tasks run on pi when pi is the provider picked in «Группы и гости», and also on their own when pi is the only provider that can serve them (no Codex or Claude ready): one `pi --mode json` child per pass with no tools, no session and thinking off, in the sandbox view with no tools, on the model picked there, else `PI_LIGHT_MODEL`, else pi's default, the first of them with a key the pass gets. The prompt goes to pi on stdin, never on its command line. A format answer cut off by the model's output limit is dropped and the raw output goes out; inline `<think>` reasoning is never sent. The address judge's fallback (no TypeSafe key, or its call failed) is the same kind of pass, and Claude and pi serve it as Codex does: it goes to the first ready of Codex, Claude and pi. Each of the three passes can be put on any provider, with its own model and depth, in «Служебные проходы» of `/settings` ([Helper passes](usage.md#helper-passes)); there pi's thinking is set by Глубина.

Your own and executors' runs on pi get Executor (when `EXECUTOR_MCP_URL` and `EXECUTOR_API_KEY` are set) and your Telegram account (when it is logged in), as on Codex and Claude; account writes still wait for your button under `TELEGRAM_ACCOUNT_WRITES=confirm`. Group runs get the chat's group memory. pi never sees the Executor key or the account token: for each run the bot opens a local port that passes the calls on, with a password of its own that pi alone gets and that stops working when the run ends. A server that does not answer within 10 seconds is left out of that run (`pi.mcp.unavailable` in the log). pi's own `mcp.json`, in `~/.pi/agent` or a project's `.pi/`, is never read.

Not yet on pi: automatic model choice and a `/settings` screen of its own.

Groups, guests and Business replies on pi get no file or shell tools, as on Claude, and pi has no web search of its own: groups get only the chat's memory, the rest chat with the model only. A photo sent with an answered group message, or one an answered message replies to, still reaches the model: the bot hands its bytes over inside the message, on Claude and Codex as on pi (a model without image input gets pi's note instead). Members get `read`, `bash`, `edit`, `write`, `grep`, `find` and `ls` in the sandbox view, with their scratch directory writable; without both `bwrap` and `socat` they are refused. The view holds pi's key and config files (`auth.json`, `models.json`, `models-store.json`, `settings.json`, `.env.local`), read-only, so a member's tools can read your keys. It reaches only the endpoint of the model the run uses, as pi itself lists the model's URL: exactly that host and port, and only at a public address.
